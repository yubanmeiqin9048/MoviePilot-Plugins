# 手动与自动流程共用搜索和下载能力

现有手动与自动流程已经共享候选下载处理，但该能力位于任务模块内部，搜索模块的对外入口则只表达人工搜索。2026-10-03 确认按能力组织代码：手动与自动流程共用 `search/` 搜索入口，将单候选下载处理提取为独立的 `download/` 能力，避免按触发方式划分两套实现。

## 已确认的边界

- 下载接收一个已选定候选，负责取得文件、解包、归属、保存和记录，并返回处理结果；具体操作继续复用现有来源、文件、归属和记录能力。
- 任务负责调度、候选选择、失败后是否继续尝试，以及将下载结果解释为任务结果。
- 保留现有手动与自动业务行为，包括候选准入、库存优先、结果保留和任务成功判定的差异；业务流程明确提供处理策略，共享下载能力不以一个手动标志隐式决定全部行为。
- 搜索也纳入本次职责调整，手动与自动共用搜索能力入口，不再仅保留人工搜索入口作为搜索模块的对外契约。
- 共享搜索返回各来源的完整候选和来源执行结果，不在内部执行业务准入、识别或排序；后续业务流程按既有顺序调用候选和归属能力。
- 搜索会话留在 `search/` 内部，由独立会话组件维护目标、候选与有效期，并校验和解析用户选择；不增加一级会话模块，也不要求自动搜索创建会话。
- 搜索不负责提交下载任务。人工下载请求入口先取得会话中的目标与候选，再交给 `task/` 提交任务，由任务调用 `download/`。

选择独立下载能力，而非继续作为任务内部的候选尝试实现，是为了让代码职责直接表达共享业务能力。人工搜索会话仍有独立职责，统一搜索入口并不意味着自动任务必须创建人工会话。

## 保持现有行为的约束

- 人工流程保留全部候选并逐条识别，单候选识别异常降级为未识别；人工查询前已有的目标信息补充行为保持原范围。
- 自动流程先做语言和翻译类型准入，再进行媒体与季集匹配；不改为全量候选先识别，也不引入人工流程的逐候选异常降级。
- 会话过期、候选失效和任务拒绝提交仍返回原有对外结果；这次职责调整不要求修改前端交互或迁移历史运行数据。
- 既有字幕保存目录、文件冲突和落盘规则继续遵循 ADR 0001。归属、记录、事件和任务终态的业务含义保持不变。

## 实施记录（2026-10-03）

用户已确认完整设计并授权实施，按以下边界完成重构：

- `search/` 对外提供 `SubtitleSearch` 和 `SearchSessions`。人工请求与自动任务注入同一搜索实例；人工识别标注、目标补充和提交编排由请求入口负责。
- `SearchSessions` 保留原有缓存区域和三十分钟有效期，仅保存目标与候选、校验选择和清理会话，不持有任务依赖。会话解析成功必须携带完整目标与候选，失败返回稳定原因。
- 单候选处理从 `task/attempt.py` 移至 `download/service.py`，由 `DownloadService.download()` 执行；下载输入、保留策略和结果独立归属 `schemas/download.py`。
- 下载以明确的直字幕信任和结果保留策略执行，不读取手动触发标志。人工任务通用失败码由任务层映射，下载仅返回处理事实。
- 对外 HTTP 路由、响应结构与错误码保留，前端及历史运行数据无需迁移。补充共享搜索、会话、独立下载、策略映射与运行态装配测试，并更新精确架构契约。
